## 0. 摘要

本报告通过**无 root 的宿主侧运行态观测**与**客户机内部 shell** 的双向取证，
并结合本版新增的**双设备对照实验**，还原了商业安卓虚拟机 VPhoneGaGa 3.4.0 的可观测架构。

本版报告的方法论底线是：

> **外部可观测行为能够约束内部架构，但通常不能唯一确定内部实现。**
>
> 而打破这一限制的唯一手段是**对照实验**：把同一份测试负载送入被测环境内部运行，
> 采集其自身返回值，并与真实内核的返回值逐项对比。差异即投影层的直接证据。

因此，全文把结论拆为三层：

| 层级 | 含义 | 允许的表述 |
|---|---|---|
| **K1 · 直接证明** | 可由实测输出（含对照实验）直接证明的语义事实 | “观测到 / 可复现 / 直接证明” |
| **K2 · 行为高度支持** | 与观测高度吻合的候选架构模型 | “现有证据最支持 / 行为高度吻合 / 候选模型” |
| **K3 · 黑盒不可区分** | 外部黑盒实验无法唯一判定的内部实现 | “无法区分 / 不能唯一确定 / 仍为候选” |

核心发现八条：

1. **系统调用投影层真实存在，但不是“接管 SVC 陷入指令”，而是自装的第二层 seccomp 过滤器。** `/proc/<pid>/status` 的 `Seccomp_filters` 给出分层证据：宿主应用进程 1 层，客户机全部进程 2 层。**K1。**

2. **`/proc` 与身份类系统调用被整体投影。** 同一进程两侧自述完全矛盾：客户机自称 `uid=0` / 全 capability / `Seccomp: 0` / 内核 4.14.42 / Cortex-A53 / 4 GB RAM；宿主内核显示 `uid=10383` / `CapEff=0` / `Seccomp: 2` / 内核 5.15.167 / 骁龙 8 Gen 2 / 14.8 GB RAM。**K1。**

3. **挂载子系统：客户机侧权限模型与 Linux 权限模型不一致，其 `mount()` 结果不能用“宿主内核按 Linux 权限规则执行同一调用”解释。** 实测：客户机内**任意 uid（含 uid 10000 / 10123）都能成功 `mount(tmpfs)`**，而真实 Linux 不可能允许 uid 10000 挂载 `tmpfs`；且 `mount` 对所有 uid 放行、`umount` 仅 root 放行（不对称）。最符合这些事实的模型是客户机存在**独立的用户态挂载语义处理**（K2），能力受 `/proc/filesystems` 白名单约束；宿主挂载表全程无变化（K1）。不能排除“用户态层转交其他宿主接口”的链路（K3）。

4. **网络为混合模型（数据面 / 控制面 / 信息面三层结论互不相同）。** 客户机内建立的监听端口出现在宿主 `/proc/net/tcp` → **宿主内核中存在真实 socket 对象（K1）**；`setsockopt(IP_RECVTTL/IP_PKTINFO/IP_RETOPTS)` 在宿主成功、在客户机返回 `EINVAL` → **控制面被用户态层拦截（K1）**；客户机内部 `/proc/net/tcp` 为空 → **信息面被投影（K1）**。数据面处理位置为候选模型（K2），其上是否叠加用户态处理无法判定（K3）。

5. **客户机的 root 是运行在 app uid 内的 Magisk 26.0 体系。** 宿主设备没有可用 root 通道，客户机 `magiskd / lspd / zygiskd64 / zygiskd32` 的宿主侧真实父进程为虚拟内核；客户机被显示的父进程是重建过的逻辑树。**K1 观测事实 + K3 成因机制。**

6. **存储层是一套私有的明文内存映射容器。** 客户机镜像**不通过内核挂载**，而由宿主侧运行时以**只读、可直接内存映射**的私有格式承载；客户机看到的块设备与文件系统是**投影**出来的。**K1 观测 + K2 解释。**

7. **一套运行在 app uid 内、以 seccomp 为拦截边界、以用户态数据模型维护操作系统语义的「系统调用投影与设备仿真层」。** 请求处理在外部行为上分为三类**语义路径**：**A 宿主能力复用 / 透传**、**B 合成 / 投影**、**C 重定向 / 虚拟文件系统**。三类描述的是**外部可观测处理结果**，不宣称为内部确定存在的三个实现分支。**K2 + K3。**

8. **本报告不把任何内部实现路径视为已经证实。** 网络、文件系统、系统调用处理等部分，本报告按对照实验结果建立候选模型，并区分 K1 结果与 K3 内部机制。

一句话概括：

> 从外部行为看，它像是在“演一个内核”；对照实验证明其**身份、系统信息、挂载、网络控制面确实由用户态代码裁决**，
> 而其**数据面（socket、mmap、时钟）复用宿主内核能力**。哪些语义被用户态接管、哪些直接透传，已由对照实验逐项划分。

## 1. 方法、权限分级与合规声明

### 1.1 方法论核心：双设备对照实验

上一版报告已确立「外部观测不能唯一确定内部实现」。本版进一步给出**打破该限制的实验设计**：

> **把同一份自编译的测试负载，分别送入“真实内核”与“投影层”运行，逐项对比系统调用返回值。**
> **差异就是投影层的直接证据；而一致性则说明该路径被透传。**

| 设计要素 | 说明 |
|---|---|
| 测试负载 | `-nostdlib -static` 裸汇编 syscall 程序（无 libc、无动态链接、无编译器运行时） |
| 排除干扰 | 不经 libc 封装，直接发起 `svc #0`，保证观测的是内核/投影层行为而非库函数行为 |
| 对照组 | 宿主（真实 Linux 5.15 内核，shell uid 2000） |
| 实验组 | 客户机（投影层，shell uid 2000 / su uid 0） |
| 判定 | 同一 uid、同一路径、同一二进制，结果不同 ⇒ 该语义由用户态裁决 |

本方法把多项旧版标注为 **U（未定论）** 的结论升级为 **K1（直接证明）**。

### 1.8 证据分档与确定性层级

| 档位 | 含义 |
|---|---|
| **A** | 无 root 即可复现（**P0 可达**） |
| **B** | 需宿主 root（**P1 可达**；早期对照载体归档） |
| **C** | 需客户机内部 shell（**P2 可达**） |
| **U** | **未定论**（现有手段无法判定） |

| 确定性层级 | 含义 |
|---|---|
| **K1** | 直接证明：可由实测输出（含对照实验）直接证明的语义事实 |
| **K2** | 行为高度支持：与观测高度吻合的候选架构模型，但非唯一实现 |
| **K3** | 黑盒不可区分：外部行为无法唯一判定的内部实现路径 |

> **原则**：越靠近“内部机制”的结论，确定性越低。“复用宿主内核”“用户态代理”“自有实现”
> 等表述，除非明确标为 K1，否则一律视为 K2 或 K3。

#### 1.8.1 标准表述句式（全文统一）

为避免把“结果”写成“实现”，全文统一采用以下句式。**K1 只描述观测事实本身，绝不描述内部实现。**

| 层级 | 句式 | 示例 |
|---|---|---|
| **K1** | **观测事实是 X。** | “客户机内 uid 10000 能成功 `mount(tmpfs)`。” |
| **K2** | **最符合 X 的架构模型是 Y。** | “最符合该差异的模型是：存在一层独立的用户态挂载语义处理。” |
| **K3** | **以下实现均可解释 X：Y1 / Y2 / Y3。当前实验无法区分。** | “用户态独立挂载表 / 用户态处理后转交其他宿主接口 / 混合实现，三者均能解释，无法区分。” |

**重要的窄化原则**（务必遵守）：

| 可以断言为 K1 | 不可断言为 K1（须降级为 K2/K3） |
|---|---|
| 客户机 `mount()` 与宿主 `mount()` **结果不同** | 客户机 `mount()` **由 `libuserkernel64.so` 实现** |
| 宿主内核中**存在**对应 socket 对象 | socket 数据面**一定直接由宿主 TCP/IP 协议栈处理** |
| 宿主内核**拒绝**该调用、客户机**接受** | 客户机内部**完全未调用宿主内核** |
| 客户机 `/proc` 输出与宿主真相**系统性不同** | 客户机 `/proc` **由某函数 hook 后合成** |

### 4.3 ★ 第二层 seccomp 过滤器 —— **A 级 / P0 / K1（核心证据）**

`/proc/<pid>/status` 的 `Seccomp_filters` 字段给出不可辩驳的分层证据：

| 进程 | `Seccomp` | **`Seccomp_filters`** |
|---|---|---|
| 宿主 `init` / `zygote64` | 0 | 0 |
| `com.vphonegaga.titan` | 2 | **1** |
| `com.vphonegaga.titan:instance1` | 2 | **1** |
| **`titan64_0:kernel`** | 2 | **2** ← 跃迁点 |
| **`titan32_0:kernel`** | 2 | **2** |
| **客户机全部进程** | 2 | **2**（100%） |

**判读**：

- Android 对每个应用进程强制安装 1 层 seccomp 过滤器（由 zygote 安装），故宿主侧恒为 1 层。
- seccomp 过滤器**只可叠加、不可移除**。层数由 1→2 的跃迁发生在 `:instance1` fork 出虚拟内核之后、客户机代码运行之前。
- ⇒ **现有证据最支持“第 2 层由客户机虚拟内核在自举阶段安装，并由其后代继承”这一解释**；
  但**具体安装调用者尚未被直接观测**。**K2。**
- 宿主设备**无 root、无 Magisk、无 Zygisk**，该层不可能来自宿主。

⇒ **VPhoneGaGa 的用户态系统调用投影确实存在，实现层为 seccomp。**
（具体策略 `RET_USER_NOTIF` / `RET_TRACE` / `RET_ERRNO` 需读 BPF 程序 —— **U 级 / K3**。）

### 4.6 ★ 挂载子系统 —— 用户态虚拟实现（客户机侧 uid 扫描）—— **C 级 / P2 / K1**

#### 4.6.1 客户机侧 uid 扫描（本子节的核心实验）

**实验设计**：在客户机内以 root 启动测试程序，`setuid` 到指定 uid 后调用 `mount(tmpfs)`，
观察不同 uid 下的返回值。测试程序为裸 syscall（`-nostdlib -static`），路径为 `/data/local/tmp/mu`。

| 目标 uid | `getuid()` 实际值 | `mount(tmpfs)` | `umount` |
|---|---|---|---|
| 0 | 0 | ✅ ret=0 | ✅ ret=0 |
| 1000 | 1000 | ✅ **ret=0** | ❌ EPERM(1) |
| 2000 | 2000 | ✅ **ret=0** | ❌ EPERM(1) |
| 10000 | 10000 | ✅ **ret=0** | ❌ EPERM(1) |
| 10123 | 10123 | ✅ **ret=0** | ❌ EPERM(1) |

**结论（K1，仅限观测事实）**：
> 客户机内**任意 uid（含 uid 10000 / 10123）都能成功 `mount(tmpfs)`**；
> 而真实 Linux 内核在任何常规配置下都**不可能**允许 uid 10000 挂载 `tmpfs`（需 `CAP_SYS_ADMIN`）。
> ⟹ **客户机的 `mount()` 结果不能用“宿主内核按 Linux 权限规则执行同一调用”来解释。**
>
> 另一个 K1 事实：**挂载权限不对称** —— `mount` 对所有 uid 放行，`umount` 仅对 uid 0 放行。
> 这种不对称本身也无法由单一内核权限模型产生。

**候选模型（K2）**：
> 最符合上述差异的架构模型是：客户机内部存在一层**独立的用户态挂载语义处理**，
> 其权限表由用户态代码自己定义（`mount` 对所有 uid 开放，`umount` 仅 root），
> 并维护一道宿主内核 VFS 不持有的挂载树。

**不可区分项（K3）**：
> 现有实验**不能**证明“该过程完全没有宿主内核参与”。理论上仍可能存在
> “客户机用户态层 → 转换 → 某个其他宿主接口 → 宿主内核”的链路。
> 本报告证明的是**结果不能用“宿主内核直接按 Linux 权限规则执行”来解释**，而非“零宿主内核参与”。

#### 4.6.2 为何**不**把“宿主 uid 2000 失败”当作对照（重要方法论更正）

> ⚠️ **本节替代早期写法。** 早期版本曾把“宿主 uid 2000 得 `EACCES` vs 客户机 uid 2000 得 `ret=0`”
> 当作决定性对照实验。**该对照是无效的**，理由如下：

- 宿主 uid 2000 调 `mount()` 得到 `EACCES`，是**标准 Linux 权限检查的必然结果**
  （缺 `CAP_SYS_ADMIN`），**与投影层无关**；它不能作为“投影层存在”的证据。
- 它只能证明“**两侧的权限模型不同**”，而**不能**证明“客户机 `mount()` 不能由宿主内核直接执行” ——
  因为在那次对照中，宿主内核**根本未被允许执行**该调用。
- 把“权限差异”当成“架构差异”，是典型的结果混淆。

**本环境无法构造宿主侧公平对照**（实测）：

| 对照方案 | 实测结果 |
|---|---|
| 宿主 root（P1）调 `mount()` | **不可用**：主载体无任何可用 root 通道 |
| 宿主 `unshare -Urm`（user namespace）后调 `mount()` | **不可用**：`unshare: Invalid argument`（内核/SELinux 禁止非特权 userns） |
| 宿主 `unshare -m`（mount namespace）后调 `mount()` | **不可用**：`unshare: Operation not permitted` |

⇒ 本报告**明确声明**：宿主侧的 `mount` 失败**仅作参照记录，不作为投影层证据**。
真正支撑结论的是 §4.6.1 的 uid 扫描、以及下面的白名单 / 宿主不可见 / 接口不一致 / 内存态四条。

#### 4.6.3 能力边界 = `/proc/filesystems` 白名单

| 客户机 `/proc/filesystems` | 挂载结果 |
|---|---|
| rootfs / proc / tmpfs / devpts / selinuxfs | ✅ ret=0 |
| socketfs / sdcardfs | ❌ 需要特殊条件 |
| **列表外**（ext2/3/4、f2fs、btrfs、overlay、squashfs、cgroup2、ramfs、debugfs、tracefs…） | ❌ **EINVAL(22)** |

宿主 `/proc/filesystems` 有 30+ 项；客户机只有 7 项。
⇒ **`mount` 实现对着这张硬编码白名单做校验。**

#### 4.6.4 语义精细度（部分实现）

| 特性 | 行为 |
|---|---|
| `-o ro` | ✅ **真正强制**（写入报 `EROFS`） |
| `-o remount,rw` | ✅ 生效 |
| `-o noexec,nosuid,nodev` | ✅ 记录并生效 |
| `-o mode=0755,uid=1000,gid=1000` | ⚠️ **只写进 `/proc/mounts` 文本，实际目录仍 777 root:root**（不实施） |
| 挂载点不存在 | ❌ `ENOENT` |
| `--move` | ❌ `EINVAL`（未实现） |
| `--bind` | ✅ `ret=0` |
| `df` 对虚拟挂载 | **不可见**（无 statfs 应答） |

#### 4.6.5 宿主侧完全不可见（K1）

- 客户机 `mount` 后，**宿主 `/proc/mounts` 无任何新增**。
- 宿主挂载表约 194 条；客户机挂载表约 48–49 条，**无一条重合的产品专属挂载点**。
- 宿主侧 grep `vphonegaga|instance1|readonly` = **空**。

**结论**：
> **「宿主 mount 表看不到 ⇒ 没有挂载能力」是无效黑盒推论。**
> 实测：客户机 `mount()` 的结果**不能由宿主内核按 Linux 权限规则执行同一调用解释**（K1）；
> 宿主内核挂载表不持有这些挂载（K1）；最符合观测的模型是客户机维护一道**用户态挂载树**（K2）；
> 能力有白名单边界，`mode/uid/gid` 等参数不实施（K1）。

#### 4.6.6 本节有效证据清单（不含无效对照）

支撑“挂载为用户态虚拟实现”的**有效**证据共 5 条，**均不依赖“宿主 EACCES 对照”**：

| # | 有效证据 | 位置 | 层级 |
|---|---|---|---|
| 1 | 客户机内**任意 uid（含 10000）均可成功 `mount(tmpfs)`**，真实 Linux 不可能 | §4.6.1 | K1 |
| 2 | 挂载权限**不对称**：`mount` 对所有 uid 放行、`umount` 仅 root | §4.6.1 | K1 |
| 3 | `/proc/filesystems` 白名单仅 7 项，列表外全 `EINVAL`；宿主 30+ 项 | §4.6.3 | K1 |
| 4 | 宿主挂载表全程无变化；`/proc/mounts` 与 `mount` 设备名不一致 | §4.6.5 / §4.5 | K1 |
| 5 | `bind mount` 破坏 `/system` 后重启实例恢复 ⇒ 挂载状态是**用户态内存态** | §10.2 | K1 |

> ❌ **不作为证据**：宿主 uid 2000 的 `EACCES`（仅参照）、宿主 `mount ext4` 的 `EACCES`
> 与客户机 `EINVAL`（权限问题 vs 格式问题，不可比）、`umount` 两侧同为 `EPERM`
> （只能证明两边都拒绝，不能证明对称性）。详见 §4.6.2。

### 4.7 ★ 网络子系统 —— 混合模型（对照实验）—— **C 级 / P2 / K1**

#### 4.7.1 socket 是真实的宿主 socket（K1）

在客户机内建立监听 socket（端口 4660 / `0x1234`），随即在宿主侧查询：

```text
宿主 /proc/net/tcp:
   5: 00000000:1234 00000000:0000 0A … uid=10383 inode=11636144   ← 真实存在！
客户机内部 /proc/net/tcp:  (空，被投影隐藏)
```

⇒ **客户机的 socket 是宿主内核的真实 socket**（uid 显示为 app 真实 uid 10383）。
⇒ 网络命名空间**与宿主共享**（宿主读虚拟内核进程的 `/proc/<pid>/net/tcp` ≈ 宿主全局连接数）。

#### 4.7.2 但 `setsockopt` 被用户态层拦截（对照实验，K1）

| socket 选项 | 宿主（真 5.15） | 客户机（投影） |
|---|---|---|
| IP_TOS(1) / IP_TTL(2) / IP_MTU_DISCOVER(10) | ✅ | ✅ 一致 |
| **IP_RETOPTS(7)** | ✅ 0 | ❌ **EINVAL** |
| **IP_PKTINFO(8)** | ✅ 0 | ❌ **EINVAL** |
| **IP_RECVTTL(12)** | ✅ 0 | ❌ **EINVAL** |
| SO_REUSEADDR / SO_KEEPALIVE / SO_RCVBUF | ✅ | ✅ 一致 |
| TCP_NODELAY / TCP_KEEPIDLE | ✅ | ✅ 一致 |
| **UDP 的 IP_RECVTTL / IP_PKTINFO** | ✅ 0 | ❌ **EINVAL** |

⇒ 宿主内核接受这些选项，客户机拒绝 ⇒ **`setsockopt` 被用户态层拦截，只放行白名单子集。**

#### 4.7.3 现象印证

- 客户机内 `ping`：`setsockopt(IP_RECVTTL): Invalid argument`，且回复 **`ttl=0`**（异常）。
- 客户机内部 `/proc/net/tcp`、`/proc/net/tcp6` **为空**；`/proc/net/sockstat` **不存在**。
- 客户机 `/proc/net/unix` 找**不到** `@titan-pipe-*`（宿主侧可见约 38 个）。

#### 4.7.4 结论

> 网络**既不是纯“复用宿主协议栈”，也不是纯“用户态协议栈”**，而是**混合模型**：
> - **数据面（K1 事实）**：客户机创建的 socket **在宿主内核中存在**（宿主 `/proc/net/tcp` 可见，uid=10383）；
> - **控制面（K1 事实）**：`setsockopt` 的部分选项被**用户态层拦截**并做白名单过滤；
> - **信息面（K1 事实）**：`/proc/net/*` 被**投影/过滤**，隐藏真实连接。
>
> **候选模型（K2）**：数据面传输很可能由宿主内核协议栈承担。
> **不可区分项（K3）**：数据面之上是否叠加了额外的用户态处理，现有实验无法判定。
>
> 「能联网 ⇒ 复用宿主协议栈」越界；正确表述应为「宿主内核中**存在**对应 socket，
> 但 socket 控制面存在用户态介入，且客户机内部不可见真实连接」。

### 4.8 硬件代理总线 `@titan-pipe-*` —— **A 级 / P0 / K1 名称枚举**

宿主 `/proc/net/unix` 对 shell 身份完全可读，暴露了客户机子系统与宿主之间的 IPC 通道名称：

```text
@titan-pipe-1-framebuffer      @titan-pipe-1-input-qwerty     @titan-pipe-1-activity
@titan-pipe-1-gsm              @titan-pipe-1-gps              @titan-pipe-1-network
@titan-pipe-1-camera           @titan-pipe-1-sensors          @titan-pipe-1-fingerprint
@titan-pipe-1-crash            @titan-pipe-1-hw-control       @titan-pipe-1-ipc
@titan-process-worker-server-1-<宿主PID>   × 95
@titan-1-process-monitor
```

- 以上为 `/proc/net/unix` 的原始名称枚举。**本报告不据此推论任何网络或通信架构。**
- 客户机内部 `/proc/net/unix` **看不到**这些名字（约 38 → 0），说明 IPC 名字对客户机隐藏。
- ⇒ **这组命名揭示了客户机外设存在代理通道**：相机 / GPS / 通信 / 传感器 / 指纹 / 图形 / 输入 /
  Activity 各自有独立的抽象 unix socket 通道。客户机内另可见产品自有属性
  `android.host.adb.port=6556`、`android.host.adb.server.port=6038`。【P2】

### 4.9 存储层 —— **B 级 / P1 观测 + K2 实现解释**

> 本节只描述**结构**，不列文件格式的字节细节（字节级描述属取证，不属架构分析）。

- 客户机镜像**不通过内核挂载**，而由宿主侧运行时以一套**私有容器格式**承载，其特征为：
  - **不加密**：客户机进程可直接对它做**只读内存映射**，映射页在客户机进程间共享；
  - **分卷组织**：每个分区由“只读数据卷 + 索引/超级块”构成；
  - 另有**可写层与缓存层**，承载客户机运行期的写入。
- **客户机看到的块设备与文件系统是投影出来的**：例如 `/proc/mounts` 显示 ext4 块设备，
  但宿主内核挂载表中并无对应实体（§4.6.5）。
- 容器内还包含一个**可解析的 Android boot 分区**，即客户机所见的 boot 也由容器提供。**K1。**

### 4.10 虚拟 Root 与 Magisk —— **C 级 / P2 / K1 形态观测 + K2 机制解释**

客户机内实测：

```text
$ su -c id
uid=0(root) gid=0(root) groups=0(root) context=--  u:object_r:toolbox_exec:s0

$ magisk -v        →  26.0:MAGISK:R
$ magisk -V        →  26000
$ ls -l /sbin/magiskinit  →  -rwxr-x--- 1 root root 642952
$ ls -l /sbin/su          →  /sbin/su -> ./magisk
```

**关于 root 来源的更正（本版修正）**：

> 早期版本写“客户机的 root 是运行在 app uid 内的 **Magisk 26.0 体系**”。
> 四状态对照（§4.14）表明该表述**不准确**：
>
> **产品自带一套 `su` 授权机制**（由客户机 `init` 直接拉起，在 Magisk 打开/关闭/重置 boot/未安装四种状态下**恒在**），
> 且该 `su` **有独立开关**可被产品管理；**Magisk 是可选的叠加层**。

**结论**：

- 产品的 root 通道是**自带的 `su`**，不依赖 Magisk；Magisk 开关只影响 Magisk 自身的启动链。
- 它能工作的外部原因是：第 2 层 seccomp 过滤器/投影层把 `getuid` / `getresuid` / `capget`
  的返回值投影为 `0` / 全 capability。**宿主内核实测同一进程 uid=10383、CapEff=0（P0）。**
- 宿主设备**无任何可用 root 通道**，故客户机 root 不可能是宿主提权的结果。
- Magisk 形态：`26.0:MAGISK:R`。⚠️ 未对二进制做官方构建的 hash 对照，不能断言“未经修改的官方原版”。**K1 形态 / K3 来源。**

### 4.14 Magisk 层的注入机制、四状态对照与版本兼容范围 —— **C 级 / P2 / K1 观测 + K2/K3 推测**

> 本节基于四份宿主侧进程采样（`process_log*.txt`，`ps -ef | grep titan` 每 0.3 秒轮询）的对比。

#### 4.14.1 四状态对照

| 状态 | Magisk 相关进程 | 组件数 | `netd` vpid | apexd 之后的 boot 链 |
|---|---|:---:|:---:|---|
| **Magisk 打开** | `magisk`(magiskinit)+`magiskd`×4+`busybox`+`sh`×6+`lspd`+`zygiskd`×2 | 117 | **60** | apexd → **magisk→magiskd→busybox→sh→lspd** → netd |
| **Magisk 关闭（未重置 boot）** | `magiskd`×2+`lspd`+`zygiskd`×2+`resetprop`（**残留**）| 115 | **60** | apexd → **magiskd→app_process** → netd |
| **重置 boot** | **0** | 102 | **42** | apexd → **netd** |
| **打开 boot，未安装任何** | **0** | 96 | **42** | apexd → **netd** |

**K1 观测事实**：

1. **“重置 boot” 与 “未安装任何” 是同一个干净状态** —— 两者 vpid 布局逐项一致
   （`ueventd`=4、`logd`=14、`vold`=23、`netd`=42、`zygote64`=43、`zygote`=44）。
2. **Magisk 层的插入点是固定的**：始终在 **apexd 之后、netd 之前**。
3. **vpid 编号随 Magisk 注入整体偏移**：`netd` 60↔42、`zygote64` 61↔43、`zygote` 62↔44
   （Magisk 插入了约 18 个进程）。
4. **产品自带 `su` 在四种状态下恒在**（由 `init` 拉起，有独立开关）。
5. **未重置 boot 时，残留的 Magisk 补丁仍会旁路拉起 `magiskd`**（其父进程是虚拟内核而非 init）。

#### 4.14.2 注入机制（推测模型，K2）

> 最符合上述观测的模型是：
> **产品并非运行“标准 Magisk 安装流程”，而是解析 boot 镜像中的 Magisk 负载，
> 用它自己实现的兼容方式直接拉起 `magiskd`。**

支持该模型的观测：

| 观测 | 为何支持该模型 |
|---|---|
| `magiskinit`（vpid 42）的父进程是**客户机 init** | 不是标准 boot 流程里的 PID 1 接管形态 |
| Magisk 阶段严格固定在 apexd↔netd 之间 | 是产品选定的**注入点**，非 Android 原生顺序 |
| 产品自带 `su`、且有独立开关 | root 通道自建，Magisk 仅叠加 |
| 未重置 boot 时 magiskd 被**虚拟内核**旁路拉起 | 产品主动解析/启动，而非走完整安装链 |

#### 4.14.3 版本兼容范围（K3 / 未确认）

- 当前实测的 Magisk 版本为 **26.0**（`26.0:MAGISK:R`）。
- 经验观察（操作者）：产品对 Magisk 版本存在**兼容范围**；更高版本可能无法拉起 Magisk，
  甚至无法启动客户机。
- ⚠️ **具体支持哪些版本并未确认**：操作者早期测试过若干版本，但**未留存记录**；
  本报告只实测了 **26.0** 一个版本。
- 因此**不应写成“仅兼容 26.0”或“锁定到某一版本”**。准确表述是：
  **兼容性存在版本依赖，具体边界未知（K3）**。

### 4.11 调度优先级 —— **A 级 / P0 / K1 观测 + K2 机制解释**

受控实验（把 VM 切到后台再切回）：

| | `instance1` | 客户机全树 |
|---|---|---|
| HOME 之前 | `cpuset:/top-app` | `cpuset:/top-app` (100%) |
| HOME 之后 | `cpuset:/foreground` | `cpuset:/top-app`（一个没掉） |
| `oom_score_adj` | `200` | `0` |

⇒ **与观测高度吻合的机制解释（K2）**：客户机进程在 **VM 启动瞬间从 `instance1` fork 时
继承了当时的 cgroup 桶与 `oom_score_adj`**，此后宿主对 `instance1` 的任何降级都不会影响已 fork 的客户机进程。

> ⚠️ **不能推出“永久”。** 本实验只覆盖了一次 HOME 切换后约 6 秒的窗口。本条标 **U 级 / K3**。

### 4.12 图形栈 —— **B 级 / P1 / K1 映射观测 + K3 实现判定**

`kgsl / ion / dmabuf` 是 Android 图形栈对**任何** GPU 渲染进程的默认路径。
外部观测到客户机 SF 持有宿主 `/dev/kgsl-3d0` 等路径；但内部究竟是完全直通、代理转发还是
用户态中转，黑盒无法唯一确定。**K3。** 真正可记录的是 §4.8 的 `@titan-pipe-*` 通道命名。

### 4.13 进程内 ELF 装载 —— **B 级 / P1 / K1 观测**

- 客户机进程**不是通过常规 `exec` 启动**的，而是由一个**进程内 ELF 装载器**
  把客户机可执行体**读入当前进程、自行重定位后跳入入口**。
- 交叉印证（P0）：所有客户机进程在宿主侧的 `Name` 字段都是该装载器；
  而宿主侧进程名（`titan{32,64}_<vpid>:<name>`）由运行时另行维护。
- 该装载器以 `.so` 名义打包进 APK，依靠安装时赋予的可执行位运行
  —— 即**不需要额外权限即可让应用自己的代码被执行**。

## 5. 架构模型

### 5.1 架构本质：三类外部可观测的处理路径

**这是理解本产品最关键的一节。**

> **术语说明（重要）**：A / B / C 描述的是**「请求 / 对象访问的处理结果与语义路径」**，
> 而**不是「内部确定存在的三个实现分支」**，也**不是「系统调用类型」**。
>
> 因为像 `/proc/cpuinfo` 这类对象，一次访问要经过 `openat()` → `read()` 等多个系统调用：
> 其中 `openat` 的外部结果可能表现为 C 路径，`read` 的外部结果可能表现为 B 路径。

客户机的每一次**请求/对象访问**，从外部行为看，处理结果可分为三类：

| 路径 | 外部可观测语义 | 是否到达宿主内核 | 典型请求 | 确定性 |
|---|---|---|---|---|
| **A · 宿主能力复用 / 透传** | 行为与宿主 Linux 语义一致 | 不能唯一确定 | `mmap`、`futex`、`nanosleep`、`clock_gettime`、socket 数据面 | **K2** |
| **B · 合成 / 投影** | 返回值或内容由客户机侧构造 | 外部结果表现为**未使用宿主真实语义** | `getuid`/`getpid`/`capget`；`uname`/`sysinfo`；`/proc/{status,cpuinfo,meminfo,version,uptime}` | **K1 结果 + K3 内部机制** |
| **C · 重定向 / 虚拟文件系统** | 对象落到客户机自己的存储体系或命名空间 | 外部可观测到真实 mmap/页缓存语义 | `openat("/system/…")`、`stat`、`mount`、`/proc/<pid>/maps` 展示层 | **K1 结果 + K2/K3 内部机制** |

**本版把挂载、网络控制面明确归入“存在不能由宿主内核直接解释的用户态语义处理”一类（K1）。**

### 5.2 系统调用投影对照表（本版核心证据）

同一二进制在两侧运行的结果汇总：

| 语义类别 | 对照结论 | 层级 |
|---|---|---|
| `uname()` / `sysinfo()` | 客户机返回合成值（内核、RAM、进程数） | **K1 投影** |
| `getuid/geteuid/getgid` | 客户机按虚拟 uid 返回 | **K1 投影** |
| `clock_gettime(REALTIME)` | 两侧秒值**完全相同** | **K1 透传** |
| `mount/umount` | 客户机侧 uid 10000 仍能 `mount(tmpfs)`，`umount` 仅 root 放行 | **K1 用户态** |
| `setsockopt(IPPROTO_IP)` | 宿主 OK vs 客户机 EINVAL | **K1 拦截** |
| `socket/bind/listen` | 客户机 socket 出现在宿主 `/proc/net/tcp` | **K1 透传** |
| `/proc/*` 内容 | 与宿主真相系统性不同 | **K1 投影** |

### 5.3 分层视图（确定性标注）

```text
┌─────────────────────────────────────────────────────────────────────┐
│ 宿主 Linux 内核 5.15.167（真实）                                     │

└─────────────────────────────────────────────────────────────────────┘
      ▲  ① 外部可观测为宿主能力路径；内部是否直接进入宿主内核为 K3
┌─────┴───────────────────────────────────────────────────────────────┐
│ L0  第 2 层 seccomp 过滤器（由客户机虚拟内核安装，全树继承）          │
│     → 截获/投影特定路径的 openat/read，返回合成内容                  │
├─────────────────────────────────────────────────────────────────────┤
│ L1  用户态内核层  libuserkernel64.so（零导出符号）                   │
│     · 用户态 VFS 对象模型（vma/dentry/inode/file）                   │
│     · 虚拟 PID / UID / capability 映射                               │
│     · 用户态挂载树（独立于宿主 VFS）★本版实测                        │
│     · socket 控制面白名单（setsockopt 拦截）★本版实测               │
│     · /proc 内容合成（→ memfd:titan-tmp-inode-N）                    │
│     · @titan-pipe-* 外设代理通道                                     │
├─────────────────────────────────────────────────────────────────────┤
│ L2  进程内 ELF 装载器  libloader64.so / libloader32.so               │
│     · 从 readonly.bin 按偏移 mmap 客户机 ELF 并自行重定位            │
├─────────────────────────────────────────────────────────────────────┤
│ L3  客户机 Android 10 系统栈（约 85–100 进程）                       │
│     init / zygote64+32 / system_server / surfaceflinger /          │
│     adbd(6556) / Magisk 26.0 / LSPosed / Zygisk64+32               │
├─────────────────────────────────────────────────────────────────────┤
│ L4  存储层：私有明文容器（非挂载、非加密）                            │
│     私有明文容器（非挂载 · 可直接内存映射 · 分卷组织）               │
├─────────────────────────────────────────────────────────────────────┤
│ L5  宿主表示层：单 Activity + 宿主 SurfaceFlinger                    │
└─────────────────────────────────────────────────────────────────────┘
```

> 图中 L0/L1 的“截获/投影”是 **K1 可观测结果**（含对照实验）；“用户态内核层”是 **K2 候选解释**；
> 其内部具体实现路径为 **K3**。

### 5.4 与 gVisor 的定位差异（不宜比较复杂度）

| 维度 | gVisor（真 LibOS） | VPhoneGaGa 3.4.0 |
|---|---|---|
| 系统调用处理 | **全部**拦截，**全部**在用户态重实现语义 | **外部语义表现为分流**：A 透传 / B 合成 / C 重定向 + 挂载/网络控制面用户态裁决 |
| 内存管理 | 自建地址空间抽象与页表 | **外部观测复用宿主 VMA + mmap 语义** |
| CPU 调度 | 两者外部均由宿主 CFS 完成 | 同左 |
| 进程隔离 | 完整沙箱 | **无任何 namespace，同 uid（K1）** |
| 网络 | 独立用户态网络栈 | **真实宿主 socket + 控制面代理 + /proc 投影（K1）** |
| 客户机“看到的” | 一个由 sentry 实现的独立内核抽象 | 一个**按路径分发的合成投影（K1 结果）** |
| 本质 | **“我造了一个内核”** | 从外部看，**“我演了一个内核”**；身份/挂载/网络控制面均有**不能由宿主内核直接解释的用户态语义处理** |
| 核心工程量 | 内核语义完备性（网络栈/内存/文件系统全部自建） | **跨进程语义垫片的正确性**（见 §5.5）；`/proc` 全字段自洽 + Magisk 兼容 + 机型适配属于其上的具体苦工 |

### 5.5 真正的工程量：跨进程语义垫片（shim）运行时

> 本节修正早期把“逐字段苦工”当成主要难点的说法。逐字段苦工确实存在，
> 但它只是**表层**；真正的难度在**架构层的多进程语义垫片**。

#### 5.5.1 与常规架构的拓扑对比

| 架构 | 进程拓扑 | syscall 处理 | 上下文由谁维护 |
|---|---|---|---|
| QEMU / KVM | **1 个主进程** + N 个 vCPU 线程 | vCPU 陷入 → VMM | VMM 独占地址空间，简单 |
| gVisor | **1 个 sentry 进程** | 陷入 sentry，Go 重实现 | sentry 独占，简单 |
| LXC / Docker | N 个宿主进程 | **直通宿主内核**（带 ns/cap） | 内核维护，无需垫片 |
| proot / ptrace | N 个宿主进程 | ptrace 拦截，**仍调用真实 syscall**（只改路径） | 内核 + tracer |
| **本产品** | **N 个宿主进程 + 每进程内垫片 + 中央 broker** | 进程内垫片捕获 → **IPC** → broker 决定语义，**且不调用特权 syscall** | **broker 维护，跨进程分发** |

**常规虚拟机的直觉是“一个主进程把整个客户机装进去”。本产品反过来：把一台客户机拆成一百多个宿主进程。**
这就是它的特殊点。

#### 5.5.2 难点逐一说明

1. **一本账要跨进程共享**
   虚拟 PID / UID / capability / cwd / fd 表 / 挂载视图 / mm 上下文，在 VM 或 sentry 里本来就**在同一个地址空间**；
   这里必须放进 broker，每个载体进程靠 IPC 去引用。**状态不在本地，而在一跳之外。**

2. **“连权限都没调”——最关键的差异**
   它**根本不进内核要权限**：`mount` / `setuid` / `capset` 这些特权调用**不发生**。
   - 因此**给它 root、给它调试权限都没用**——它压根不发起那个特权 syscall；
   - 权限判定完全由 broker 自己的策略表完成；
   - 这正是“**uid 10000 也能 mount、且 mount/umount 不对称**”的原因（§4.6.1）。
   ⇒ 在真实系统里“调一下内核就能解决”的事，在这里**必须自己把语义写完**。

3. **每个 syscall 都可能跨进程**
   一次调用 = 参数捕获 → 序列化 → IPC → broker 决策 → 回程 → 回填寄存器。
   需要处理并发、顺序、超时、背压、消息清理。
   ⇒ 等于**在没有内核帮忙的情况下自建一套分布式 RPC，还要对外表现为单机内核**。

4. **进程生命周期要镜像**
   `fork` / `exec` / `exit` / task-death 必须同时反映到载体进程与 broker；
   还涉及孤儿回收、subreaper 语义、上下文生命周期同步。

5. **把重活丢给宿主操作系统**
   调度（CFS）、页缓存、`mmap` / VMA、GPU、真实 socket——这些**不重写，直接借**。
   这是它能在 app 沙箱里跑起来的**前提**，也是“一部分计算任务完全丢给操作系统”的含义。

6. **代价：双账本一致性**
   一部分语义来自宿主内核真相，一部分是用户态模拟，两边还必须看起来一致。
   ⇒ 这正是 `/proc` 与 `mount` 相互矛盾、`/proc/net/*` 与真实 socket 不一致的根源。

#### 5.5.3 一句话概括

> 它是**用“多进程拓扑 + 全语义垫片”去模拟“单进程 LibOS”**，同时把昂贵的数据面委托给宿主内核。
> 难的不是拦截本身，而是：
> **在没有内核帮忙维护上下文的前提下，让一百多个宿主进程对外表现为一台一致的 Android 设备。**
> 这也解释了为什么这不是常规项目能轻易做出来的东西。
>
> 工程层面的**复现路线与垫片设计（含高性能设计）**另见 [`复现路线与垫片设计.md`](复现路线与垫片设计.md)。

### 5.6 最小架构模型（压缩后的骨架）

把已经取得 K1 支持的部分压缩掉，可以得到如下最小模型——它足以回答
“如果要做一件类似的事，需要做什么”这个问题：

```text
                    ┌──────────────────────────────┐
                    │   Guest semantic projection   │
                    │   （用户态语义投影层）         │
                    └──────────────┬───────────────┘
        ┌──────────────────────────┼──────────────────────────┐
        ▼                          ▼                          ▼
  synthetic semantics       virtual objects            host-backed
  （用户态合成）             （用户态维护）              （宿主承载）
        │                          │                          │
  · PID / UID / capability   · /proc 视图                · real socket
  · uname / sysinfo          · mount tree                · mmap / VMA
  · /proc 部分内容           · Android 文件系统视图       · clock
                             · 虚拟设备状态               · GPU fd
                                                          · host IPC buffers
        └──────────────────────────┼──────────────────────────┘
                                   ▼
                              Host Linux kernel
```

**三列的含义**（对应 §5.1 的 A/B/C 路径）：

| 列 | 语义 | 对应路径 | 确定性 |
|---|---|---|---|
| **synthetic semantics** | 客户机侧直接合成，宿主无对应真实语义 | B | K1 结果 |
| **virtual objects** | 状态由用户态维护，宿主内核不持有 | B / C | K1 结果 |
| **host-backed** | 外部行为复用宿主内核能力 | A | K1 对象存在 / K2 处理位置 |

**外设 IPC**（`@titan-pipe-*`：framebuffer / input / camera / GPS / sensors / fingerprint…）
是本模型右侧的延伸：客户机外设统一经抽象 unix socket 由宿主代理。

**由此得到的工程定位**：

> 不是“写一个 Android 模拟器”，而是
> **“做一个运行在普通 Android app UID 下的 Android 用户态执行环境，
> 再给它补一层足够完整的 Linux/Android 语义投影，
> 并把无法或没必要虚拟化的能力接回宿主。”**

**⚠️ 该模型的性质**：三列划分是对**已取得 K1 支持的事实**的分类，
不是内部实现分支的断言；每列内部的真实实现仍为 K2/K3。

## 6. 系统启动流程（观测 + 推定）

1. **宿主实例引导** —— 宿主 zygote fork 出 `:instance1`；加载 `libVPhoneGaGaLib.so`，
   建立 JNI 通道，打开实例的**私有容器卷**。
2. **虚拟内核初始化** —— `:instance1` fork `titan64_0:kernel`；该进程**为自己安装第 2 层 seccomp 过滤器**；
   解析**容器索引**，构建用户态 VFS；建立虚拟挂载树。
3. **系统调用虚拟化上线** —— 此后 fork 出的所有进程均继承 seccomp 过滤器，进入“客户机”语义空间：
   PID / UID / capability / `/proc` / 挂载 / 网络控制面全部被投影。
4. **特权进程孵化** —— 客户机 init 被虚拟内核拉起后，`magiskd` / `lspd` / `zygiskd64` / `zygiskd32`
   依次出现，其宿主侧**真实父进程均为虚拟内核**。
   **机制未定论**：可能是直接孵化，也可能是 `PR_SET_CHILD_SUBREAPER` 重父化。**K3。**
   与此同时，客户机侧被投影出一棵“符合真机形态”的逻辑父子树。
5. **系统服务与图形** —— `titan64_1:init` 解析 `init.rc` 拉起约 70 个系统服务；
   客户机 SurfaceFlinger 通过 `@titan-pipe-1-framebuffer` 把合成结果交给宿主单 Activity 显示。
6. **客户机 adbd** —— 监听 6556（`android.host.adb.port=6556`），提供内部调试入口。

| # | 原措辞（过强） | 改为 | 理由 |
|---|---|---|---|

```bash
adb -s $G shell 'su -c id'
adb -s $G shell 'cat /proc/self/status | grep -E "Uid|CapEff|Seccomp|NoNewPrivs"'
adb -s $G shell 'grep CPU /proc/cpuinfo | head -3; grep MemTotal /proc/meminfo; cat /proc/uptime; cat /proc/version'

# ── 伪造自证：同一状态多个答案 ──
adb -s $G shell 'head -2 /proc/self/mountinfo; head -2 /proc/mounts; mount | head -2'

# ── ★ 挂载能力：客户机侧 uid 扫描（有效实验）──
# 在客户机内以 root 启动，setuid 到目标 uid 后再 mount
# 实测：uid 0/1000/2000/10000/10123 均可成功 mount(tmpfs)；umount 仅 uid 0 成功
adb -s $G push mntuid /data/local/tmp/
for u in 0 2000 10000; do adb -s $G shell "su -c '/data/local/tmp/mntuid $u'"; done
# 白名单：客户机 /proc/filesystems 仅 7 项
adb -s $G shell cat /proc/filesystems
# 注意：宿主侧的 EACCES 仅作参照，不作为证据（宿主无 root、不允许 userns）

# ── ★ 网络对照实验 ──
# 在客户机建监听 socket，宿主侧查询
adb -s $G shell 'toybox nc -l -p 4660 &' &   # 或用自编译程序 bind(0.0.0.0:0x1234)
adb -s $H shell "cat /proc/net/tcp | grep -i '1234'"       # 应出现，uid=10383
adb -s $G shell "cat /proc/net/tcp"                         # 应为空（投影）

# ── 客户机 root 形态 ──
adb -s $G shell 'magisk -v; magisk -V; ls -l /sbin/magiskinit'

# ── 对照实验专用：自编译裸 syscall 程序 ──
# 用 -nostdlib -static 自编译一个直接发 svc #0 的小程序，push 到 /data/local/tmp 后
# 在两侧各运行一遍；对比 mount/setsockopt/uname/sysinfo 的返回值即可。
adb -s $H push raw_syscall /data/local/tmp/ && adb -s $H shell /data/local/tmp/raw_syscall
adb -s $G push raw_syscall /data/local/tmp/ && adb -s $G shell /data/local/tmp/raw_syscall
```

## 10. 取证过程中遇到的问题、事故与更正（诚实记录）

本节如实记录本次取证中**遇到的问题、发生的失误、以及被推翻的旧写法**。
记录这些的目的不是免责，而是维护报告可信度：**一份复盘报告出现错误是正常的，关键是把问题写出来并说明如何更正。**

### 10.1 误删 adb 密钥导致连接授权中断【已恢复】

- **问题**：为排查客户机 adb `unauthorized`，删除了 `~/.android/adbkey*` 并重启 adb server。
  这导致已建立的授权全部失效，客户机 adb 短暂中断。
- **后果**：破坏了既有取证连接，需重新建立授权。
- **更正**：此后只做 `adb kill-server` / `adb connect`，**不再删除密钥**；重新授权后恢复。
- **教训**：排查连接问题的首选手段是重启 server，而不是清空凭证。

### 10.2 `bind mount` 破坏客户机 `/system` 投影【已恢复】

- **事故**：`bind mount /system` 到「已叠加挂载的目标」（该目标已有 `tmpfs` / `proc` 叠加）后，
  客户机 `/system` 投影失效（`/system/bin/sh`、`/system/bin/toybox`、`/system/build.prop` 全部变为
  `No such file`，`adb shell` 无法启动，因其固定 exec `/system/bin/sh`）。
- **原因**：客户机的用户态挂载实现对「向已挂载目标做 bind mount」处理有缺陷，
  覆盖/解绑了源 `/system` 的 VFS 映射。此为**内存态破坏**，容器文件在磁盘上未改动。
- **恢复**：重启客户机实例后完全恢复（`/system/bin/sh` 299616 B、`/system/bin/toybox` 恢复，
  残留挂载清除，挂载表恢复约 48 条）。
- **后续处置**：改用 `/data/local/tmp` 作为挂载目标，每个测试后立即 `umount`，
  **不再对系统路径做 `bind mount`**。
- **方法论意义**：该事故本身证明——**客户机的挂载状态是用户态内存态，而非宿主内核态**；
  重启 App 即可完全重置，宿主内核从始至终不持有这些挂载。

### 10.3 测试程序传 NULL 指针导致数据污染【自查更正】

- **问题**：一版 `setsockopt` 测试程序把 `optval` 传成 `0`（NULL），
  导致 `SO_REUSEADDR` 等本应成功的选项全部返回 `EINVAL`。
- **后果**：若不修正，会错误得出结论“socket 选项大量不支持”。
- **更正**：重写程序改用有效指针，并重新做**双侧对照**，才得到正确结论（仅 `IPPROTO_IP` 部分选项被拦截）。
- **教训**：被测程序的自身 bug 与投影层行为要用**对照实验**区分。

### 10.4 一度错误地删除了 P1（最高权限）观测归档【本版已恢复】

- **问题**：在撰写 v2.0 时，因本机当前只有 P0 + P2 层级，曾写下
  “本报告无 P1 层级”，并删除了早期在带 root 对照载体上取得的 P1 观测。
- **更正**：**P1 观测不应因载体不在场而删除**。本版已完整恢复：§2.2（对照载体）、
  §4.2（命名空间 / 挂载）、§4.4（`maps` / `fd`）、§4.9（存储）、§4.13（ELF 装载器）。
- **教训**：删证据比加结论危险得多；报告应保留历史取证记录。

### 10.5 本版自身的实验设计缺陷：【已更正】

#### 10.5.1 “宿主 EACCES vs 客户机 ret=0” 是无对照实验

- **问题**：v2.0 初稿的 §4.6.1 把“宿主 uid 2000 得 `EACCES` vs 客户机 uid 2000 得 `ret=0`”
  当作“决定性对照实验”。
- **为何无效**：宿主 uid 2000 调 `mount()` 得到 `EACCES`，是**缺 `CAP_SYS_ADMIN` 的必然结果**，
  与投影层无关。该对照只能证明“**两侧权限模型不同**”，不能证明“客户机 `mount()` 不能由宿主内核执行”——
  因为在那次对照中，宿主内核**根本未被允许执行**。把“权限差异”当成“架构差异”是结果混淆。
- **本环境无法构造宿主侧公平对照**（实测）：主载体无 root；`unshare -Urm` → `Invalid argument`；
  `unshare -m` → `Operation not permitted`。
- **更正**：§4.6.1 已重写为**客户机侧 uid 扫描**（任意 uid 含 10000 均可 `mount(tmpfs)`），
  并在 §4.6.2 明确声明宿主侧失败**仅作参照，不作为证据**。
- **教训**：对照实验必须保证两侧**被测因素处于同一可取值的状态**；当一侧因环境限制根本无法成功时，
  两边的差异反映的是环境限制，而不是被测机制。

### 10.6 早期分析的认知偏差【本版更正】

| # | 早期偏差 | 本版更正 | 定位 |
|---|---|---|---|
| 1 | 「宿主 mount 表看不到 ⇒ 没有挂载能力」 | 客户机 uid 10000 仍能 `mount(tmpfs)` + 白名单 + 宿主挂载表无变化 | 实例方法残缺 |
| 2 | 「能联网 ⇒ 复用宿主协议栈」 | 混合模型（真实 socket + 控制面拦截） | 结果倒推实现 |
| 3 | 「简单库劫持，就地处理」 | 跨组件 IPC + 用户态 VFS + 挂载树 | 模型简化 |
| 4 | 「宿主看不见 ⇒ 功能不存在」 | 用户态自建语义，宿主本就不可见 | 范式盲区 |
| 5 | 把 A/B/C 当作「内部三个实现分支」 | 改为「外部可观测的三类处理路径」 | 措辞越界 |
| 6 | 把“逐字段苦工/`/proc` 自洽”当作主要工程量 | 主要工程量是**跨进程语义垫片运行时**（见 §5.5）；逐字段只是表层 | 把表层当难点 |
